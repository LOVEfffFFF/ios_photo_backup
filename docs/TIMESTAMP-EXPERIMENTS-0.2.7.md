# Fixed persisted adjustment timestamp experiment (0.2.7)

0.2.6's primary DNG import-date option failed on an edited 50% Effect ProRAW sample. The actual exported plist still uses capture time, while original DNG, rendered JPEG, capture time and complete recipe remain intact. Independent reinspection confirms that only the date differs. No timestamp fix is enabled in normal restore.

The third-party [17.6.1 PHAssetCreationRequest decompilation](https://github.com/SuperChaoM/iPhone15-3_17.6.1_21G101_Restore/blob/95df6b804bee0e01538eb2ddad0413609938d063/System/Library/Frameworks/Photos.framework/PHAssetCreationRequest.m#L7985) reconstructs adjustments using the internal capture date, then applies a creation request's custom properties later. Its [PLManagedAsset implementation](https://github.com/SuperChaoM/iPhone15-3_17.6.1_21G101_Restore/blob/95df6b804bee0e01538eb2ddad0413609938d063/System/Library/PrivateFrameworks/PhotoLibraryServices.framework/PLManagedAsset.m#L14774) uses a general key-path setter. [PLUnmanagedAdjustment.willSave](https://github.com/SuperChaoM/iPhone15-3_17.6.1_21G101_Restore/blob/95df6b804bee0e01538eb2ddad0413609938d063/System/Library/PrivateFrameworks/PhotoLibraryServices.framework/PLUnmanagedAdjustment.m#L1) propagates its adjustment timestamp to the owner. These are not Apple documentation/source or the exact 17.7.2 binary, and decompilation can be inaccurate. They motivate an experiment, not a proven fix.

The new `customAdjustmentDate` variant supplies exactly one fixed creation property:

`additionalAttributes.unmanagedAdjustment.adjustmentTimestamp`

Its value is the typed original date from the verified `com.apple.photo/1.9.1` backup plist. It does not change the original DNG, backup bytes or capture date. It uses an undocumented `setCustomAssetProperties:` setter; availability, authorization and behavior remain unverified on the device. The request getter is checked before adding resources. Only the named variant configures this dictionary on a new asset creation request. Debug commands cannot supply arbitrary keys, selectors or values. Other variants and normal restoration do not use it. Source data, logs and credentials stay outside Git.

The bridge requires the phone to advertise the capability, the user to select a backed-up still photo and to permit copy experiments. Existing attempt bounds, sequential tasks, copy journal and result retry rules continue. An older/read-only phone, an inspection request with this variant or an arbitrary key-path command is rejected.

The first device trial should create one copy of the same 50% sample. Independently compare source/backup/download/result DNG, JPEG and full actual plist bytes; decode the complete compressed/inflated recipe, capture date and source existence. A setter/getter, database date or successful transport is insufficient. If the actual plist date and bytes do not match, keep the failure. If they match, separately inspect again, test persistence/repeatability and verify Photos RAW/revert/re-edit controls before considering normal restoration. The unmapped `3DSilverplate` name remains a separate limitation and cannot become a false full-restore success.

Build verification and device results were pending at this plan's first commit. The Release build and all automated checks subsequently passed; the one-copy device trial failed. Its actual full plist still changes only the edit date from 06:39:47 to capture time 06:28:05 Beijing. An independent copy inspection confirms the same bytes/date; separate source inspections confirm both sources remain unchanged. DNG, render, complete compressed/inflated recipe and fractional capture date match. The setter/getter succeeded but did not establish file persistence. See [0.2.7 validation](VALIDATION-0.2.7.md).

Further inspection distinguishes `persistMetadataToFilesystem` from `_writeOutAdjustmentsToFile:`: the former persists general asset attributes in a different record. In the sampled implementation, the adjustment plist is written in the earlier adjustment-ingestion path, before custom properties are applied. A later unmanaged adjustment date update does not by itself prove that the plist is rewritten. This explains why the earlier implementation clue was insufficient, but the exact device-side database state and internal cause remain unverified.
